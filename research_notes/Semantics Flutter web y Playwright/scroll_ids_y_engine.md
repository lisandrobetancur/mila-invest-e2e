# Flutter web semantics (flt-semantics): SCROLL and IDENTIFIER problems, engine history, and Playwright techniques

Scope note: research done on 2026-11-19. Version anchors confirmed from sources: 3.19 (15 Feb 2024), 3.22 (14 May 2024), 3.24 (7 Aug 2024), 3.27 (11 Dec 2024), 3.29 (12 Feb 2025), 3.32 (20 May 2025), 3.35 (13 Aug 2025), 3.38 (12 Nov 2025) ([Archive of What's new](https://docs.flutter.dev/release/archive-whats-new)). Issues filed in Oct–Nov 2026 report "3.47.x stable" ([#194549](https://github.com/flutter/flutter/issues/194549), [#196446](https://github.com/flutter/flutter/issues/196446)). The web-accessibility docs page says it reflects "Flutter 3.50" ([docs](https://docs.flutter.dev/ui/accessibility/web-accessibility)). I could not find official release dates for 3.41/3.44/3.47/3.50. Confidence labels used below: **[multi]** = confirmed by several sources, **[single]** = one source, **[inference]** = my reasoning, not stated by a source.

## Q1. History of Semantics.identifier / flt-semantics-identifier on web, and why a child id goes missing (P8, merged semantics, AppBar)

### Takeaway
`Semantics.identifier` shipped in the framework in 3.19 (Feb 2024) for Android/iOS. Web support (the `flt-semantics-identifier` attribute) came from engine PR #53278, merged 20 Jun 2024, and was working on TextButton in 3.24.1. Since then three kinds of bug have been fixed or are still open: TextField identifiers missing on web (fixed Jun 2025), identifier nodes being merged into ancestors (an implicit-boundary rule now exists, which one source dates between 3.41.9 and 3.44.9), and identifier-only changes not being pushed to the engine (open, Nov 2026). P8 (a child id lost under MergeSemantics, ListTile or a merging button) is expected behaviour for merged subtrees. The fix belongs in the app's widget tree, because Playwright cannot recover an id the framework never sent.

### Cited Findings
**Introduction and web support**
- The `identifier` property was contributed by the Maestro team (engine PR 47961) and is "available in Flutter 3.19+". This was for native accessibility (Android resource-id, iOS accessibilityIdentifier). — [Maestro docs](https://docs.maestro.dev/platform-support/flutter)
- An April 2024 Selenium article says the identifier, added in 3.19.0, "does not work on the Web". At that time people used `//flt-semantics[contains(@aria-label, "...")]` and clicked `flt-semantics-placeholder` inside `flt-glass-pane`'s shadowRoot. — [Habr, 22 Apr 2024](https://habr.com/en/articles/809137/) (pre-3.24; outdated on the identifier point)
- Before web identifiers existed, issue #97455 (Jan 2022) asked for a testID/class on web DOM nodes. yjbanov had earlier said "We cannot support adding stable IDs to HTML nodes generated by the engine" (#95624). Community workarounds from 2022–2023: `Semantics(label:)` / `semanticsLabel` to get `aria-label`, `cy.contains()` text queries, clicking `flt-semantics-placeholder`, or moving to integration_test/Patrol. On 7 Jun 2024 mdebbar proposed `cy.get('[flt-semantics-identifier="my-test-id"]')`. The issue was closed 20 Jun 2024 via **flutter-team-archive/engine PR #53278**, and an autoroll on 21 Jun 2024 added the attribute. On 24 Jun 2024 mdebbar said semantics behave the same under the HTML and CanvasKit renderers. — [flutter/flutter#97455](https://github.com/flutter/flutter/issues/97455)
- Docs PR #149915 (mdebbar, Jun–Jul 2024) updated the `SemanticsProperties.identifier` docs to point at engine PR #53278. The draft text said `semantics-identifier`, but the published docs say `flt-semantics-identifier`. — [flutter/flutter#149915](https://github.com/flutter/flutter/pull/149915)
- Current API docs: "On web, this will set a `flt-semantics-identifier` attribute on the DOM element that corresponds to the semantics node." Also: "When set, this property implicitly forces the creation of a new SemanticsNode (equivalent to setting container to true in Semantics). This ensures the identifier is always attached to its own node and is not merged into an ancestor." It can be matched with `CommonFinders.bySemanticsIdentifier`. — [api.flutter.dev SemanticsProperties.identifier](https://api.flutter.dev/flutter/semantics/SemanticsProperties/identifier.html)

**Identifier-related bugs**
- **#155323, "Wrapping a TextField with Semantics.identifier doesn't work on the Web"**: opened 17 Sep 2024 on 3.24.1. The attribute appears on a wrapped TextButton but not on a TextField. It was reproduced on 3.24.3 and 3.26 master. yjbanov (3 Oct 2024): "I suspect the identifier is lost on the framework side as a result of node merging." **Closed** 12 Jun 2025 by **PR #170395**. — [#155323](https://github.com/flutter/flutter/issues/155323)
- **PR #170395**, "Fix Semantics.identifier on TextField not working on web", merged 12 Jun 2025. Root cause: in the web engine, a dirty `identifier` was not applied to a `SemanticRole` that had no `SemanticBehavior`s. It has no milestone, and a later issue (#172921) reports the problem still present on 3.32.8. — [PR #170395](https://github.com/flutter/flutter/pull/170395)
- **Boundary rule change between versions** (single third-party source): on Flutter **3.44.9**, `config.isSemanticBoundary = container || (_properties.identifier != null)`, so an identifier always gets its own node. On **3.41.9** that rule did not exist, and a bare `Semantics(identifier:)` was merged into the ListView item node. The fix there was `MergeSemantics` + `Semantics(identifier:)` wrapped around the IconButton, which produces one node carrying the id, the tap action and the tooltip. Same PR: on iOS an identifier-only node with no label, value or action is not an accessibility element. — [bannzai/medicalarm PR #389, 14 Oct 2026](https://github.com/bannzai/medicalarm/pull/389); the rule is also quoted in [FabricElements/fabric_flutter PR #309](https://github.com/FabricElements/fabric_flutter/pull/309)
- PostHog (tested on Flutter 3.44.8): "Flutter puts the identifier on a parent `group` node rather than on the button node itself". To match clicks on it they recommend an "Elements chain contains" filter. — [PostHog Flutter docs](https://posthog.com/docs/libraries/flutter)
- **#196446** (OPEN, opened 12 Nov 2026, 3.47.9): changing only `Semantics.identifier` never reaches the engine, because `_isDifferentFromCurrentSemanticAnnotation` doesn't compare the identifier. Reported on iOS/Android and not tested on web. It is hidden when a label changes at the same time. Linked open PR #196460. — [#196446](https://github.com/flutter/flutter/issues/196446)
- #165562, a similar stale-identifier report, was closed after a Widget Inspector check on 3.29.0. The #196446 reporter argues that check only verified the framework tree. — [search summary via #196446](https://github.com/flutter/flutter/issues/196446)
- Related merge-logic work: PR #183745, "Update merge semantics logic to merge sibling nodes" (chunhtai), and #191095 (an assertion `node.isMergedIntoParent` when a sibling merge group appears inside MergeSemantics). — [PR #183745](https://github.com/flutter/flutter/pull/183745), [#191095](https://github.com/flutter/flutter/issues/191095) (titles from search results; details not fetched)
- PR #163843 added `semanticsIdentifier` to `Text` widgets. — [PR #163843](https://github.com/flutter/flutter/pull/163843) (title only; status and version not verified)

**Widgets missing from the tree (AppBar title)**
- A commit dated 3 Oct 2025, "Fix AppBar web accessibility: prevent more items announcements", changes four `Semantics` wrappers in `app_bar.dart` (title header, flexibleSpace, the appBar wrapper, the outer appBar) to `explicitChildNodes: !kIsWeb`. On web, AppBar descendants are therefore no longer forced into separate child nodes, and they merge upward. It references issue #176332. — [googlesource commit](https://flutter.googlesource.com/mirrors/flutter/+/refs/heads/back_1003%5E%21)
- The web `headingLevel` (1–6) maps to `<h1>`–`<h6>`. The boolean `header` is now a no-op on Android/iOS. — [breaking change: semantics header/headingLevel](https://docs.flutter.dev/release/breaking-changes/semantics-header-heading-level)

### Inferences
- **P8 root cause [inference, consistent with the API docs and #155323]:** `identifier` makes its own widget a boundary, but `MergeSemantics` / `mergeAllDescendants` on an ancestor (ListTile, buttons, AppBar on web after Oct 2025) folds descendant nodes into the ancestor. The ancestor's node is the only one sent to the engine, so the child id never reaches the DOM. No Playwright technique can recover it. The options are:
  1. Put the identifier on the merging ancestor itself, e.g. `Semantics(identifier: 'row-x', child: ListTile(...))`. That is also what medicalarm did with `MergeSemantics(child: Semantics(identifier:…, child: IconButton))`. **[single + inference]**
  2. Where the child really needs to be its own target, give it its own node (`Semantics(container: true, explicitChildNodes: true)`, or drop the merge) and accept the accessibility change. **[inference]**
  3. Locate through the ancestor's id and refine by role or text: `page.locator('[flt-semantics-identifier="row-x"]').getByRole('button')` or `.filter({ hasText })`. **[inference]**
- **Version sensitivity [single]:** on Flutter < ~3.44 an identifier-only `Semantics` can itself be merged into a list item. On ≥ 3.44 it forces its own node but may land on a `role="group"` wrapper rather than on the clickable node (PostHog). In Playwright, clicking `[flt-semantics-identifier=x]` usually still works because the group overlays the same rect. For role assertions, use `locator('[flt-semantics-identifier=x]').locator('[role=button]')`, or the reverse with `:has()`. **[inference]**
- **AppBar title [inference]:** on web after the Oct 2025 change, the title text is merged into the AppBar header node. Locate it by text (`getByText` / `getByRole('heading')` if `headingLevel` is set) or put an identifier on the AppBar or a wrapper, not on the inner `Text`.
- **Stale ids after reorder [inference from #196446]:** if a list reorders and only the identifier changes, the DOM attribute may keep the old value (the issue is framework-side, so web is probably affected too, though not tested). Prefer ids that are stable per item, not per index.

### Gaps
- No release note or changelog names the first stable release with `flt-semantics-identifier`. #97455 + #155323 show it was present by 3.24.1, and engine PR #53278 merged 20 Jun 2024, which suggests 3.24 **[inference]**.
- I couldn't find which stable release first contains PR #170395 (merged 12 Jun 2025; probably 3.35 **[inference]**) or the PR that introduced `isSemanticBoundary = container || identifier != null` (dated only by medicalarm's 3.41.9 vs 3.44.9 comparison).
- No official doc says whether an ancestor `MergeSemantics` overrides an identifier's implicit boundary. The API doc says it "is not merged into an ancestor", which seems to contradict P8. That sentence probably refers to implicit merging, not explicit `MergeSemantics`. Not confirmed; worth a quick probe in our `semantics-probe/`.
- I found no flutter/flutter issue that specifically discusses ListTile or button identifiers lost under `mergeAllDescendants` on web.

## Q2. Scrolling in semantics mode (P4): flt-semantics-scroll-overflow, scrollTop sync, wheel jumps, lazy lists

### Takeaway
On web, a semantics scrollable keeps a real DOM scroll container (`flt-semantics-scroll-overflow`). Its `scrollTop` mirrors the Flutter offset, and child nodes are translated by that adjustment. When the browser scrolls that element, the engine converts the change into scroll actions or offsets. Several bugs live in this sync: jumps of about 80% of the viewport when wheeling over nested or non-scrollable children (#159680, reportedly fixed by mid-2025), clamped `scrollTop` when the extent grows (#194549, open), and stale offsets after a list stops scrolling so taps land on the wrong row (#195469, open, fix PR #195578). Lazy lists only build visible items, so off-screen rows have no DOM node. The community answer is a bounded "scroll a step, re-query" loop driven by `mouse.wheel` over the scroll container.

### Cited Findings
**How the semantics scrollable works (from bug reports, 3.47.x code)**
- The scrollable node has an overflow element whose real browser scroll position mirrors the Flutter scroll offset. `_updateScrollableState` copies `element.scrollTop`/`scrollLeft` into `verticalScrollAdjustment`/`horizontalScrollAdjustment`, and `recomputeChildrenAdjustment` adds them to each child's translation so DOM nodes line up with the painted rows. — [#195469](https://github.com/flutter/flutter/issues/195469)
- `SemanticScrollable.update` assigns `element.scrollTop` *before* `_updateScrollableState()` resizes `flt-semantics-scroll-overflow`, so the browser clamps it. `_recomputeScrollPosition` then sends a wrong `scrollToOffset`. In the repro, a 40px scroll up moved the list 440px (Row 20 to Row 9). — [#194549](https://github.com/flutter/flutter/issues/194549)
- Engine PR #53922, "[web] fix unexpected scrolling in semantics" (yjbanov, merged 16 Jul 2024): scrollable containers always get `role="group"` so the browser doesn't merge child text into one string, and `preventScroll` defaults to true when focusing, which relates to the scroll-on-focus problem in #130950. — [engine PR #53922](https://github.com/flutter-team-archive/engine/pull/53922)

**Scroll bugs**
- **#159680, "[web] enabling semantics breaks scrolling"** (opened 2 Dec 2024, 3.24.4; confirmed on 3.24.5 and 3.27 master; labelled regression). Scrolling an outer scrollable over a nested widget "suddenly jumps", even when the nested widget is a single-line TextField that can't scroll. yjbanov's explanation: the engine fails to detect smooth scrolling and issues `SemanticsAction.scrollUp`, which scrolls about 80% of the viewport in one frame. In-thread workarounds: hide the nested semantics node; wrap the inner widget in a translucent `GestureDetector` with no-op `onTapDown`/`onPanUpdate` (worked consistently for the reporter); `touch-action: none` on the node (inconsistent); a custom engine with the scroll-action lines in `_recomputeScrollPosition` removed. Users said it was fixed on master/beta in May 2025 and on the latest stable in Aug 2025. It was **closed for no response** 26 Aug 2025, with no fixing PR linked. — [#159680](https://github.com/flutter/flutter/issues/159680)
- #159358, "jerky scrolling with EnsureSemantics() and a non-scrollable inner widget": closed (title from the engine PR #53922 page; not fetched). — [engine PR #53922](https://github.com/flutter-team-archive/engine/pull/53922)
- **#194549** (OPEN, P2, opened 16 Oct 2026, 3.47.4/3.47.7, no PR): scrollTop clamping when one update both grows the extent and moves past the old max. The real case was a type-ahead list where `Scrollable.ensureVisible` grew the extent in the same frame. — [#194549](https://github.com/flutter/flutter/issues/194549)
- **#195469** (OPEN, P2, opened 28 Oct 2026, 3.47.7, Chrome 156; assigned flutter-zl): when a list shrinks so it can no longer scroll, `_cleanUp()` removes the overflow element but leaves the adjustments and scrollTop stale. Children are then offset, so a tap on painted Row 2 activates Row 0. `removeProperty('overflowY')` uses camelCase and is ignored by Chrome. The reproduction used `await page.mouse.wheel(0, 300)`. The horizontal axis is suspected to be a separate issue, because the post-update callback writes only `scrollTop`. — [#195469](https://github.com/flutter/flutter/issues/195469)
- **PR #195578** (OPEN, opened 29 Oct 2026, approved by flutter-zl 3 Nov 2026, blocked on a "Google testing" check as of 6 Nov): adds `_resetScrollOffsets()` on the non-scrollable path and recomputes child positions. Tested with dart2js and dart2wasm (CanvasKit). — [PR #195578](https://github.com/flutter/flutter/pull/195578)
- Older wheel issues outside semantics: #71324 (wheel blocked when hovering SelectableText/TextField on web) and #35723 (configurable wheel handling in ListView). — [#71324](https://github.com/flutter/flutter/issues/71324), [#35723](https://github.com/flutter/flutter/issues/35723) (pre-2023; titles only)

**Lazy lists and community Playwright techniques**
- Flutter lists are virtualised and canvas-scrolled, and off-screen items are "not in the semantics tree". The proposed helper is `scrollUntilVisible(locator, { within, maxSwipes })`, which scrolls by "wheel/drag on the scrollable semantics node" (implemented 10 Nov 2026). — [YuraBerez/playwright-e2e-kit #3](https://github.com/YuraBerez/playwright-e2e-kit/issues/3)
- `locator.scrollIntoViewIfNeeded` on a Flutter semantics node failed in CI with "Element is not attached to the DOM": the transient semantics node was detached while Playwright waited for stability. The fix removed it, read the bounding rect from the DOM atomically with frame polling, and scrolled the Flutter canvas to the top explicitly before measuring (merged 12 Oct 2026). — [Pixelhub PR #2](https://github.com/abolfazl2600/Pixelhub/pull/2)
- General Playwright guidance for virtualised lists: advance in bounded steps, re-resolve the locator after each render, and assert with `toBeInViewport()` on the target rather than `toHaveCount` on the dataset. — [qaskills.sh](https://qaskills.sh/blog/playwright-locator-scroll-into-view-lazy-lists) (generic, not Flutter-specific)

### Inferences
Playwright techniques for P4, with confidence:
- **Bounded wheel loop over the scroll container, re-querying each step** **[multi: playwright-e2e-kit, the #195469 repro, generic guidance]:** hover the centre of the scrollable's semantics node (the `flt-semantics` that contains `flt-semantics-scroll-overflow`, or one with a known identifier). Then loop `page.mouse.wheel(0, step)` → wait a frame or two (`page.waitForFunction(() => new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r))))`) → `if (await target.count() && await target.isVisible()) break`. Cap it with maxSteps and detect end-of-list when the container's bounding content stops changing. Keep `step` well under the viewport height (e.g. 100–200px) so off-screen items get built and appear in the tree.
- **Avoid wheeling over nested, focusable or non-scrollable children** (TextField, chips, inner scrollables) **[single (#159680) + inference]:** position the mouse over a part of the scrollable with no nested semantics nodes (padding, a static text row), or over the scroll-overflow element's edge. The jump in #159680 came from the engine misreading the scroll as a discrete `scrollUp/Down` action.
- **Don't rely on `scrollIntoViewIfNeeded()` on flt-semantics nodes** **[single (Pixelhub) + inference]:** it fails for nodes that aren't built yet (lazy lists) and can throw "not attached" on transient nodes. When the node exists, `locator.evaluate(el => el.scrollIntoView({block:'center'}))` makes the *browser* scroll the overflow element, which the engine then syncs back. That path is exactly what #194549 and #195469 exercise, so verify positions afterwards.
- **Set `element.scrollTop` on the overflow container directly** **[inference; mechanism from #194549/#195469]:** `container.evaluate((el, y) => { el.scrollTop = y; el.dispatchEvent(new Event('scroll')); }, y)`. The engine listens to the scroll event and recomputes the Flutter offset. It is deterministic, but it goes through the same buggy sync path. Use small increments and re-check `boundingBox()` before clicking.
- **Tap misalignment guard** **[inference from #195469]:** after a list shrinks (filter, delete), semantics nodes can be offset from the paint. Before clicking, assert that the target node's `boundingBox()` matches expectations, or click by identifier rather than by coordinates. If clicks land on the wrong row, scroll the list or force a re-layout (navigate away and back) to reset it. Track #195469 / PR #195578.
- **Keyboard scrolling** **[inference, no source found]:** focusing a semantics node inside the list and pressing PageDown/ArrowDown depends on Flutter's Shortcuts/Scrollable keyboard handling, not on the semantics DOM. I didn't find it documented for semantics mode.
- **App-side alternative [inference]:** expose a test hook (e.g. a `--dart-define=E2E=true` debug button or deep link) that calls `Scrollable.ensureVisible` / `ScrollController.jumpTo`. This is deterministic but white-box.

### Gaps
- I found no issue literally titled with `flt-semantics-scroll-overflow` other than #194549's description, and no design doc for the SemanticScrollable sync algorithm.
- #159680 has no linked fixing PR or version, and the reporter never confirmed the fix. Whether the "80% jump" can still happen on 3.47 with a wheel over a non-scrollable child is unverified, so our P4 may be this same bug or a variant.
- I found no source on how Playwright's `mouse.wheel` (a CDP `mouseWheel` event) differs from a trackpad's smooth scroll in triggering the engine's "smooth scroll detection".

## Q3. ensureSemantics(), the placeholder / "Enable accessibility" button, cost of keeping semantics on, and renderer differences

### Takeaway
Web semantics is off by default "for performance reasons". You turn it on either with the hidden `flt-semantics-placeholder` button (`aria-label="Enable accessibility"`) or with `SemanticsBinding.instance.ensureSemantics()`, which returns a `SemanticsHandle` that keeps collection on until disposed. Keeping it on adds per-frame work and changes how taps are delivered to pointer-level gesture code. The semantics DOM is built by the shared web engine layer, not the renderer. A maintainer stated that HTML and CanvasKit behave the same, and the HTML renderer has since been removed, leaving CanvasKit and Skwasm.

### Cited Findings
- "For performance reasons, Flutter's web accessibility is not on by default." Users press an invisible button with `aria-label="Enable accessibility"`, after which "the DOM tree will reflect all accessibility information". In code: `if (kIsWeb) SemanticsBinding.instance.ensureSemantics();`. In multi-view or embedded apps the placeholder is scoped per Flutter view. — [docs.flutter.dev web accessibility](https://docs.flutter.dev/ui/accessibility/web-accessibility)
- `ensureSemantics()` "Creates a new SemanticsHandle and requests the collection of semantics information". "Once all outstanding SemanticsHandle objects are closed, semantics information are no longer collected." The doc has no web-specific notes. — [api.flutter.dev ensureSemantics](https://api.flutter.dev/flutter/semantics/SemanticsBinding/ensureSemantics.html)
- PostHog (tested on Flutter 3.44.8): "With semantics on, Flutter places a `flt-semantics` node over each widget and tappable nodes receive the click." "Semantics adds per-frame work on web. If a screen has many widgets, profile it before and after you turn semantics on." "Semantics also changes how Flutter Web delivers taps": code using `Listener`, `onTapDown`/`onTapUp` or custom gesture recognizers needs testing, while `onPressed`/`onTap` keep working. Flutter already enables semantics when a screen reader is active. — [PostHog Flutter docs](https://posthog.com/docs/libraries/flutter)
- The DOM structure is an `flt-semantics-host` parent with `flt-semantics` and `flt-semantics-container` children, positioned over the painted widgets. — [Medium / Flutter blog, "Accessibility in Flutter on the Web"](https://medium.com/flutter/accessibility-in-flutter-on-the-web-51bfc558b7d3) (older article; date not verified)
- Placeholder activation from automation: `document.querySelector('flt-semantics-placeholder').click()` (Flutter driver workaround). Maestro and Appium struggled because the placeholder is offscreen. — search summary of [rhythmo #385](https://github.com/mhdolatabadi/rhythmo/issues/385) / [flutter PR #65051](https://github.com/flutter/flutter/pull/65051) (not fetched in full). An older form went through the shadow DOM: `document.querySelector('flt-glass-pane').shadowRoot.querySelector('flt-semantics-placeholder').click()` — [Habr, Apr 2024](https://habr.com/en/articles/809137/). The npm `@rentready/flutter-selenium-bridge` clicks the placeholder too — [npm](https://www.npmjs.com/package/@rentready/flutter-selenium-bridge)
- #195585 (title only): on desktop, a screen reader reading forward never reaches the "Enable accessibility" placeholder, and Tab reaches it last. — [#195585](https://github.com/flutter/flutter/issues/195585)
- 3.38 (12 Nov 2025): the "What's new" blog mentions `SliverSemantics` and that iOS can enable semantics by default via `ensureSemantics`. — search summary of [What's new in Flutter 3.38](https://blog.flutter.dev/whats-new-in-flutter-3-38-3f7b258f7228) (not fetched directly)
- **Renderers:** the current docs list only CanvasKit and Skwasm (JS via dart2js, Wasm via dart2wasm with `--wasm`). — [Web renderers](https://docs.flutter.dev/platform-integration/web/renderers). The HTML renderer deprecation was announced in Aug 2024 (`--web-renderer=html|auto` to stop working). — [flutter-announce](https://groups.google.com/g/flutter-announce/c/JqkMe7cPkQo); [Final announcement](https://groups.google.com/g/flutter-announce/c/fngDlrI-nvY). A Stackademic blog dates the flag removal to 3.29 and the code removal to 3.32 **[single]** — [Stackademic](https://blog.stackademic.com/the-javascript-exit-flutter-web-beyond-javascript-211b5eeaf994)
- mdebbar (24 Jun 2024): semantics behave the same under the HTML and CanvasKit renderers. — [#97455](https://github.com/flutter/flutter/issues/97455)
- PR #195578's author ran the engine semantics tests with both dart2js and dart2wasm (CanvasKit), so the semantics code is compiled and tested under both targets. — [PR #195578](https://github.com/flutter/flutter/pull/195578)

### Inferences
- **Semantics DOM vs renderer [inference, supported by mdebbar's statement and the shared `lib/web_ui` semantics code]:** the `flt-semantics` tree is generated by the web engine's semantics layer independently of CanvasKit or Skwasm, so locators should carry across a switch to `--wasm`. Timing (first frame, font loading) can differ. This is unverified for Skwasm specifically.
- **Prefer `ensureSemantics()` behind a define over clicking the placeholder [inference]:** e.g. `const e2e = bool.fromEnvironment('E2E'); if (kIsWeb && e2e) SemanticsBinding.instance.ensureSemantics();`. It removes a race at startup and avoids focus quirks with the offscreen placeholder. Clicking the placeholder (`page.locator('flt-semantics-placeholder').click({force:true})` or a `dispatchEvent('click')`) is the black-box fallback for builds you can't change. I found no source for a standard `--dart-define` name. Our current approach (always on) is equivalent but adds per-frame cost in production.
- **Behaviour drift with semantics forced on [single (PostHog) + #159680]:** pointer-level gesture code (`Listener`, `onTapDown`, drag recognizers) and scroll behaviour can differ from a production session without semantics. Tests run with semantics on may not catch bugs that only appear with it off, and the reverse.

### Gaps
- No quantitative benchmark of the semantics cost on web (frame time or memory) from an official source.
- No official statement or release note comparing semantics between Skwasm and CanvasKit, and no official doc on when the HTML renderer code was removed (only a single blog).
- Whether `flt-semantics-placeholder` still lives inside a shadow root in current versions was not verified. Selectors from 2024 used `flt-glass-pane` shadowRoot; Playwright's CSS engine pierces open shadow roots anyway.

## Q4. Major web-semantics refactors and API changes 2024–2026 (3.19 → 3.47/3.50) and plans that could affect DOM-based automation

### Takeaway
2024–2026 brought several changes to the web semantics DOM. The web engine was reorganised around `SemanticRole` + `SemanticBehavior` classes. A public `SemanticsRole` API arrived (3.32, May 2025) and maps to ARIA roles on web. Flags were refactored into a `SemanticsFlags` class. `headingLevel` maps to `<h1>`–`<h6>`. Per-widget web tweaks such as AppBar `explicitChildNodes: !kIsWeb` (Oct 2025) and the Slider `<input type="range">` (3.50) followed. Each of these can change the tag, `role`, or node nesting an automation locator depends on. `flt-semantics-identifier` has stayed stable since 2024. I found no public plan to remove or rename it.

### Cited Findings
- 3.32 (20 May 2025): "You can now improve accessibility of your apps with SemanticRoles". — [Archive of What's new](https://docs.flutter.dev/release/archive-whats-new)
- The `SemanticsRole` enum (e.g. `SemanticsRole.list`, `listItem`, `slider`) on web: "these Flutter-specific roles are translated into corresponding ARIA roles in the web page's HTML structure". — [web accessibility docs](https://docs.flutter.dev/ui/accessibility/web-accessibility). ### Inferences
- **Locator robustness [inference]:** prefer `[flt-semantics-identifier=...]` (stable since mid-2024) and Playwright's `getByRole`/`getByLabel`. Those follow ARIA rather than tag names, which have changed: `<input type=range>` for sliders, `<h1>`–`<h6>` for headings, `role=group` wrappers added on scrollables and removed in menus. Avoid structural CSS such as `flt-semantics > flt-semantics-container > ...`, since role/behaviour refactors and merge-logic changes (#183745) reshuffle nesting.
- **Upgrade checklist [inference]:** when bumping Flutter, re-run a DOM snapshot of key screens (e.g. `page.locator('flt-semantics-host').ariaSnapshot()`). Watch for (a) identifiers moving between group and button nodes (3.41 → 3.44 boundary rule), (b) AppBar and other `!kIsWeb` merges, (c) scroll-sync fixes (#195578) changing tap alignment.
